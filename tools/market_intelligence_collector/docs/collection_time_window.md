# 采集时间窗

`collect --time-window 30d` 按本次运行开始时刻检查**文章来源的发布时间**。
命令行原有默认值仍为 `30d`；API 不传 `time_window` 或传空值时可进行历史采集。
非法值、零或负数会报错，不会悄悄关闭过滤。

## 日期依据

- 识别文章发布元数据、与当前页面对应的 JSON-LD Article.datePublished、文章发布头字段，以及搜狐主文章头部 `#news-time`。
- 不将正文的业务日期、业绩期间、URL 日期、搜索摘要日期、dateModified 或数据库写入时间当作发布时间。
- 多个发布字段跨日期冲突，或没有识别到发布字段时，标记为时效待核实。
- 没有时区的时间按 Asia/Shanghai 解释。仅精确到日期的字段按当地自然日比较，截止日包含在内；带时间的字段按准确时间比较。
- PDF 暂无可信发布元数据解析，因此在限时采集中作为时效待核实链接保留，不以 PDF 正文出现的日期放行。

通过时间窗仅表示文章发布于该范围，不表示其中每一条历史业务数据也发生在该范围。
原有事实、关系、日期及数值证据校验继续执行。

## 处理顺序与缓存

正文读取后，在正文模型提取、内容哈希去重/复用之前检查时间窗。
超窗、未来日期、日期未知或冲突的来源保留链接和读取诊断，不进入正文模型提取或结构化分析入库。
搜索候选筛选仍可使用批量模型分类；时间窗检查不把搜索引擎的日期猜测当作文章发布证据。

有时间窗时，跨运行 URL 缓存必须重新读取文章并检查发布日期。
只有通过检查后才可复用相同内容哈希的已有分析；历史缓存不能绕过当前时间窗。
未提供时间窗的历史采集保留原有缓存行为。

## 报告与排查

`collection_diagnostics.time_window_filter` 包含基准时间、截止时间、通过数量、
`filtered_by_reason` 以及被过滤的链接和原因。读取诊断同时保存 `publication_time` 的证据来源。

- `outside_time_window`：文章过旧。
- `future_publication_time`：文章时间晚于本次运行基准。
- `publication_time_unverified`：时效待核实，包含缺少明确字段或日期冲突。

全部成功读取的候选都被过滤时，`output_status=time_window_filtered`、`usable=false`。
这是内容时效过滤，不是模型/API 调用失败。覆盖缺口中也会记录各类过滤数量。

这次补丁不修改本机模型配置。已部署的 65536 输出 token 上限继续生效。
