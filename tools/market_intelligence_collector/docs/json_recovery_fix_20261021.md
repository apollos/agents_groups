# JSON 格式失败后的一次模型重新生成

2026-10-21。本轮已完成本地实现、同步及远程 Ubuntu 离线验证。
解决的是来源抽取返回非法 JSON 后没有显式恢复机会的问题；上游为何缺括号尚未定位，
本轮没有真实模型请求，也不改变 B6 的业务验收结论。

## 实际行为与配置

正文抽取先执行原有模型策略。若没有任何成功解析的结果，且末次为 `json_invalid`，
在预算允许时，使用该次模型配置、同一份原始来源材料、任务和统一审核规则重新生成一次。
整个 MIC run 最多一次，不把坏 JSON 加入证据，不执行补括号或公司关键词规则。
原失败状态、正文及诊断保留；新响应独立接受严格解析、schema、共享内容审核、日期窗口及入库检查。

开关位于 `config/call_governance.yaml`：

```yaml
call_governance:
  extraction:
    json_recovery:
      enabled: true
```

未配置时也默认开启；设为 `false` 可关闭。恢复消耗既有 run、source、Gateway 和时间预算，
可能减少后续来源的调用名额，不增加总额度。提取、分块、恢复与仲裁现在累计共享同一来源调用上限。
普通 fallback 已得到可解析结果时不触发恢复；证据不足、低置信度、schema/内容审核失败、
网络失败及 `output_truncated` 均不因此重试。初筛、视觉、仲裁和分块提取不触发此机制。
分块仅有一次来源额度时仍发送一个分块，不退回整篇超长材料。

恢复提示词追加到原 system 指令；原 user 材料不变，保留 32000 字符配置及 65536 输出 token 上限。
请求 timeout 使用本次 run 剩余秒数；SDK timeout 不是整体硬截止保证，外层 worker 仍负责总时限。
预算检查与实际预留之间若发生取消/超时，可能记录一次被拒绝的模型尝试而没有 HTTP 发送；
实际发送数以 `gateway_requests_sent` 为准。

## 审计与停止边界

新增 `json_recovery` 诊断，记录恢复策略、一次上限、父响应 SHA256、可用的父请求/trace ID。
入库时关联 `parent_model_run_id`，ModelRun 分别保存各次 token 和估算费用；
报告与 explain 可读回父子关系、各次状态和输出 token，运行摘要保留总费用。
完整原始正文仍只在启用受限 acceptance trace 时保存；本轮没有默认开启正文日志。
trace 的输入 256 KiB、响应 2 MiB、run 32 MiB 和调用条数上限保持。

抽取调用正常返回 pipeline 后，先保存已经发生的调用审计，再检查取消/截止，
随后才准许导航、发布日期更新和业务写入。进程强杀、崩溃或调用尚未返回不在此审计保证范围内。
因此模型请求期间超时或取消时仍能读回两次调用与费用，但迟到结果不能形成正式事实、指标或日期。
共享语义审核模块及规范未修改，测试没有放宽其准入要求。
